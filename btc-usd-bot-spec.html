BTC/USD custom trading bot — build specification

A self-hosted BTC/USD signal bot, meant to run unattended on the author's own VPS (Docker + Traefik already in place). Build in the phases listed in Section 13 — each phase independently runnable and testable before the next. Alert-only and paper-trading phases come first; live trading is not skipped to.

1 Scope & Goals

  • Monitor BTC/USD price action and fire custom signals not available in mainstream free tools (e.g. TradingView's free tier).
  • Deliver alerts via Telegram in real time.
  • Optionally (later phase, opt-in) support semi-automated or fully automated execution.
  • Run entirely on the author's own VPS — $0 recurring cost beyond the VPS itself.
  • Config-driven: strategy parameters editable without touching code.

2 Constraints

  • No paid data feeds, no paid backtesting/SaaS tools.
  • Must run unattended and recover from crashes (Docker restart policy or systemd).
  • Secrets (API keys, bot tokens) via environment variables / .env, never hardcoded or committed.
  • Most crypto exchanges quote BTC/USDT, not literal BTC/USD. USDT is functionally equivalent to USD for this purpose.
  • Data vs. custody split (Nigeria-specific): Binance is used strictly as a read-only public data source — historical/live OHLCV and funding-rate data, no API key, no funds ever touch it. All order placement and fund custody happens on Quidax, a Nigerian SEC-provisionally-licensed exchange with direct NGN bank rails and a bot-friendly REST API — sidestepping Binance's shifting Nigeria-specific restrictions while keeping Binance's much deeper history for backtesting. Fee-wise the two are close to equivalent (both 0.1% taker on order-book trades), so this split is a risk decision, not a cost one.

5 Data Layer

  • Use ccxt's Binance adapter in public/read-only mode only — no key or secret required for OHLCV candles or funding-rate data.
  • Poll or stream OHLCV candles (WebSocket preferred for latency; REST polling is fine to start — e.g. every 1–5 min depending on the strategy's timeframe).
  • Store candles in a local table: candles(exchange, symbol, timeframe, open_time, open, high, low, close, volume).
  • Backfill enough historical data (ideally 2–3 years) to backtest across different market regimes, not just recent bull conditions — Binance's history is far deeper than Quidax's, which is why it's used for this layer.
  • Respect exchange rate limits — ccxt exposes these; don't poll faster than needed.
  • Separately, backfill Quidax's own BTC/USDT order-book depth and recent trade history so live signal execution is checked against Quidax's actual tradable liquidity, not just Binance's — the two can diverge, especially in size.

6 Strategy Engine

  • Build a pluggable strategy interface (a base class with a generate_signal(df) -> Signal | None method) so multiple strategies run side by side and swap via config, not code.
  • Each strategy reads its parameters from a config file — timeframe, indicator periods, thresholds, position sizing rule.
  • A Signal event carries: symbol, timeframe, direction (long/short/flat), entry price, stop-loss, take-profit, confidence/reason string, timestamp.
  • A market regime filter (ADX, realized volatility, or price vs. SMA(200)) decides which sub-strategy is "live" — the part that's genuinely different from one static TradingView alert. An independent reproducible backtest (CoinQuant, BTCUSDT daily, 2021–2026, fees included) found an SMA(200) trend filter drove the best risk-adjusted result of the strategies tested (profit factor 2.02) — worth backtesting as the primary switch, ADX as secondary confirmation.
NATR regime filter — findings Normalized ATR (ATR/price) vs. its own trailing history — a different axis from ADX/SMA200 (volatility expansion vs. trend strength/extension), on the premise BTC moves in volatility clusters. On BTC/USDT 2020–2023 (donchian trend, flat ranging): NATR gave 10 trades, +9.33% return, −4.77% max DD, 70% win rate, PF 4.90; ADX on the identical window gave 12 trades, +7.52%, −2.74% max DD, 50% win rate, PF 4.93 — nearly identical profit factor despite different mechanics. Neither result is trustworthy alone at 10–12 trades — same sample-size caveat that already burned the rsi_bb evaluation. Treat as "no evidence NATR is better, no evidence it's worse." Deployed default stays adx.

7 Candidate Strategies for BTC/USD

None of these are guaranteed profitable — they're starting points to implement, backtest, and tune. Crypto markets shift between regimes often; treat every number below as a first guess to validate on real data, not a final setting.

a) Trend-following: EMA cross + ATR trailing stop

implemented, not deployed

Long when a fast EMA (e.g. 20) crosses above a slow EMA (e.g. 50) on a higher timeframe (4h or 1D), exit via an ATR(14)-based trailing stop (e.g. 2× ATR) rather than a fixed target. Works well in sustained directional moves; tends to whipsaw in choppy, range-bound conditions — pair with the regime filter so it's only "live" when trend strength (ADX ≳ 20–25) confirms a trend.

b) Mean-reversion: RSI + Bollinger Bands in range regimes

tested — not deployed

In detected range-bound conditions (low ADX), fade extremes — RSI(14) < 30 near the lower Bollinger Band as a long signal, RSI > 70 near the upper band as a short. Works in sideways chop; loses badly if it fires during a real trend, which is why gating it behind a regime filter matters.

c) Volatility breakout: Bollinger Band squeeze + expansion

deployed — shadow-testing

BTC tends to move in volatility clusters — long compression (tight Bollinger Bands / low ATR) often precedes a sharp expansion. Enter in the breakout direction; a stop just inside the pre-breakout range. False breakouts are the main failure mode.

Implemented as VolatilityExpansionBreakoutStrategy (bot/strategy/vol_expansion.py), without the original idea's volume-confirmation half (a candidate future refinement, not yet built). Band width, normalized by price, counts as a "squeeze" at or below its own rolling squeeze_percentile over squeeze_lookback bars — self-relative, like NatrRegimeFilter. A signal only fires when the bar before the breakout was squeezed, width is now expanding, and price closes beyond the prior bar's band edge (a same-bar band would be pulled wide enough by its own extreme close to hide the breakout — same reasoning as donchian's shifted channel). Deployed standalone, no regime filter — no backtest verdict logged yet.

d) Crypto-specific: funding-rate mean-reversion

deployed — shadow-testing

Perpetual futures funding rates are public and often overextend at sentiment extremes — very high positive funding correlates with over-leveraged longs (pullback risk), very negative with over-leveraged shorts. Pulled read-only via ccxt's Binance funding-rate endpoint (Quidax is spot-only). Used as a filter/confirmation only — the trade still executes on Quidax's spot market.

Implemented as FundingFilteredStrategy (bot/strategy/funding_filter.py): wraps a base trend strategy (default donchian) and vetoes a new long when funding exceeds high_threshold, or a new short when funding is below low_threshold — a veto, not its own entry rule. Thresholds default ±0.0005, an untested guess. Funding data comes from a separate binanceusdm client and its own table, looked up per bar via as-of/backward alignment. Live shadow runs refresh it every iteration via Strategy.before_poll(). Deployed as donchian_funding_filtered — no verdict logged yet, evaluated live per "testing hypotheses is cheap now."

e) Trend-following: 20-bar Donchian breakout

deployed — control

Long when price closes above the highest high of the prior 20 daily bars, exit when it closes below the lowest low of the prior 20. In the referenced independent backtest, the single best performer by raw return (+118.4% over 2021–2026 on BTCUSDT, 24 trades, 50% win rate, PF 1.45) — but also the largest drawdown of the trend strategies tested (48.6%, concentrated in the 2022 bear market). Cheap to implement — just a rolling max/min comparison.

f) Market-structure breakout + retest

weak, not pursued further

Find the most recent confirmed swing high/low (a fractal), wait for a breakout close, wait for a retest of that level, then enter on confirmed rejection/continuation. Deliberately a different hypothesis from (a)/(e) — those ask "what do the indicators say," this asks "what is price actually doing."

On BTC/USDT 2020–2023: best-of-9 in a swing_window/retest_window sweep was PF 1.22 (67 trades, +9.37% return, −14.5% max DD) — every combo clustered in a narrow, unremarkable PF 1.0–1.22 band. Clearly weaker than donchian's PF 3.94 on the identical window. Recommendation: don't deploy or tune further as designed — a tested, logged negative result, same treatment as rsi_bb. The core idea may still have merit with a different rule set (tracking multiple unresolved swing levels, or requiring volume/momentum confirmation), but that's a distinct redesign.

Explicitly not included: naive grid trading. The most heavily marketed "profitable" crypto bot strategy, but the claims behind it are almost entirely exchange marketing, and its mechanics are structurally built for sideways markets — a strong sustained trend leaves it holding unrealized losing positions, the same failure mode that made the Bollinger mean-reversion strategy the worst performer in the real test (65.7% win rate, only +10.4% return, 52.7% drawdown). If added later, it needs a hard "pause during confirmed trend" kill-switch, not a standalone always-on strategy.

Evidence note Strategies (a) and (e) were validated against an independent, reproducible backtest (CoinQuant, BTCUSDT daily, Jan 2021–Aug 2026, 0.1% taker fees included, spans the 2021 bull run, 2022 crash, 2023–26 cycle). None of the five families tested there beat plain buy-and-hold Bitcoin on raw return — their edge was a much smaller drawdown and far less time exposed to the market. Treat that as the realistic bar: a better risk profile than holding, not a guarantee of beating it.
  • Risk a small, fixed percentage of capital per trade (0.5–1%), sized off the stop-loss distance, not a fixed coin amount.
  • Cap max concurrent open positions.
  • Add a daily/weekly loss circuit-breaker that pauses the bot after a max drawdown threshold, rather than trading through a bad stretch.
  • Avoid leverage until the strategy has a solid live track record on paper; if used later, keep it conservative.

8 Backtesting Requirements

  • Include realistic taker fees — Quidax's actual 0.1% order-book fee, since that's where trades execute — plus a slippage assumption. Backtests without fees/slippage are misleading.
  • Test across multiple distinct BTC regimes (2020–21 bull run, 2022 bear market, a choppy/sideways stretch), not just recent months.
  • Use walk-forward or out-of-sample validation, not just an in-sample fit — curve-fitting to past data is the biggest risk.
  • Track more than total return: Sharpe ratio, max drawdown, win rate, and profit factor all matter.
  • Single-sample-path caveat: BTC has only one historical price path (~6–7 years of meaningful data). A public study and this project's own backtests draw on largely the same history — that overlap means they aren't independent confirmations of each other. Cross-asset validation (Phase 3.5) is the practical way to get independent evidence without waiting years for fresh candles.
Pilot backtest findings An initial sweep found rsi_bb produces only 2–5 trades across a 4-year window regardless of parameters, with results swinging from +$138 to −$449 on small threshold changes — not enough trades to distinguish a real edge from noise, and it did not beat plain donchian on the identical window. Recommendation: don't deploy rsi_bb as designed; "stay in cash while ranging" is the more defensible default (adopted). Separately, donchian with a widened exit channel (20/55) looked strong in-sample on 2020–23 (PF 3.94, 64.3% win rate) but came back essentially breakeven out-of-sample on 2024+ (PF 0.91, 50% win rate) — no confirmed edge yet on BTC alone.

Holdout enforcement — methodology fix The "out-of-sample" test above wasn't actually clean — the donchian exit-channel-width exploration (30/55/70/90) ran against 2023-01-01 onward with no end date, overlapping almost entirely with the same window later used as the 2024+ holdout. Going forward, config.yaml's validation.holdout_start marks a reserved window: sweep can never touch it, backtest excludes it unless --allow-holdout is explicitly passed, and every deliberate use is logged to notes/holdout_validations.md. Doesn't retroactively clean the data already looked at — makes the mistake structurally harder to repeat going forward.

9 Alerting Layer

  • Create a bot via Telegram's BotFather, grab the bot token and target chat ID.
  • Alert types: signal fired (entry/stop/target/reason), daily summary, a heartbeat/error alert so the user knows if the process dies — a silent bot is worse than no bot — and, since 2026-09-09, a near-miss alert.
  • Keep the message format consistent and parseable (structured, not free text) in case it's parsed programmatically later.
Sanity-checking against your own reading of the market · 2026-09-09 A signal-fired alert only tells you when a strategy did act — nothing about whether it should have and didn't, exactly the failure mode a silent bug would produce. Every Strategy now exposes diagnose(df) -> dict: its current read of the market plus a near_miss flag for "a human would plausibly expect an entry soon" — even when generate_signal returns nothing. Three ways to see it:
  1. python main.py diagnose --strategy <name> — prints the current diagnosis on demand, from the exact same config/override plumbing as shadow, backfilling fresh data first.
  2. The daily Telegram summary appends diag_* fields from the diagnosis.
  3. A NEAR_MISS alert fires the first time near_miss turns true, de-duplicated on a stable category key (not the human-readable reason, which can embed drifting numbers) so a persisting condition alerts once, not every 5-minute poll.

Implemented for the four strategies actually deployed with a meaningful "why didn't this fire" story: DonchianBreakoutStrategy (proximity to either channel edge), MultiTimeframeTrendPullbackStrategy (HTF trend confirmed, daily pulled back, reclaim not yet closed — the canonical "pullback after trend" case), VolatilityExpansionBreakoutStrategy (currently squeezed, watching for a breakout), and FundingFilteredStrategy (base strategy would fire, but funding is vetoing it — more actionable than a generic near-miss, so it takes precedence). RegimeSwitchedStrategy.diagnose merges in whichever sub-strategy the regime says is currently "live." Strategies not in active shadow-run use (ema_cross, rsi_bb, market_structure) fall back to the base no-op default.

9.5 Manual-Trading Recommendation Layer · 2026-09-09

A second, independent alert channel — not the automated Quidax-fee shadow-run simulation, and not Section 10's Quidax execution path. The user trades BTCUSD manually via MetaTrader 5 through Exness (a CFD venue, not spot) and wanted the same strategy logic to produce advisory entry/exit recommendations for that discretionary trading, reviewed and acted on by hand — the bot never places an order anywhere, on any venue, in this layer either.

  • python main.py recommend: one process runs every strategy listed in config.yaml's recommend.strategies (defaults to the same five configs the shadow runs use, extensible with one more YAML line — no code change). One shared candle backfill/Binance poll per cycle rather than one per strategy — the whole point was resource-sharing.
  • Reuses, unchanged: Strategy/diagnose(), the Binance candle data the shadow containers already backfill, bot/backtest/engine.py's open_position/check_exit/close_position (fee/slippage swapped for Exness CFD-cost placeholders, not Quidax's spot fee — untested, tune to your actual account), and the shadow runner's own alert-scheduling helpers directly. A recommendation's "currently open" position is tracked via the exact same paper_position/paper_trades/signals tables, just under a reco_-prefixed strategy_label (e.g. reco_donchian_adx_control) so it can never be confused with a real shadow-run paper trade.
  • Market-wide sentiment context: bot/data/sentiment.py fetches the Crypto Fear & Greed Index (alternative.me, public/free/no key), refreshed at most once/day, stored in a fear_greed_index table. Advisory context only, attached to recommendation alerts — deliberately not wired into any strategy's entry/exit rule; that would be a new, separately-backtested strategy variant, not "just report it."
  • Explicitly out of scope for now: a live Exness/MT5 data feed (signals stay sourced from Binance spot candles — a flagged spot-vs-CFD approximation, not claimed identical) and a live Telegram↔Claude sentiment bridge (asked about, then paused — a real, separate future feature, not built).

Alert lifecycle, per recommendation

RECOMMENDATION_ENTRY
entry · stop · target
→
RECOMMENDATION_STOP_UPDATE
zero or more, while open
→
RECOMMENDATION_EXIT
stop · take_profit · end_of_data

Exactly one entry (always carries entry=/stop=/target= — the stop is the initial invalidation level), stop-updates only while open and only for trailing-stop strategies, then exactly one exit closing it out — a past entry alert is never ambiguous about whether it's still "in play." Current state is also visible on demand via a strategy's daily summary position= field (flat vs. long since …).

Reading the daily summary's diag_* fields diag_near_miss=False always pairs with a blank diag_near_miss_reason= — the reason is None whenever there's no near-miss to explain, and the formatter renders None as an empty string rather than omitting the field. Not a bug; the reason only carries real text once diag_near_miss=True.

10 Execution Layer (Optional, later phase) — Quidax

  • Build a thin custom REST client against Quidax's documented API (quidax.com/developers/api_v2) for account/balance lookup, order-book snapshot, placing/cancelling orders — the one piece that can't reuse ccxt.
  • Generate the API key scoped to trading only — no withdrawal permission on the bot's key, ever. Withdrawals stay a manual, human action.
  • Start in "alert + manual confirm" mode (bot proposes a trade, user confirms via Telegram reply) before enabling full auto-execution.
  • Prefer limit orders over market orders on Quidax's order book to control slippage (order-book trades get the 0.1% fee; the "instant swap" convenience feature charges 1% and should be avoided).
  • Keep the same daily-loss circuit breaker from Section 7 active at the execution layer too, as a second safety net.
  • Log every order request/response verbatim (minus the API key) — Quidax's API is far less documented/battle-tested than Binance's.

11 Storage & Logging

  • SQLite tables: candles, signals, trades, equity_curve.
  • Structured logs (not just print statements) with rotation so the VPS disk doesn't fill up over months of unattended running.

12 Deployment on the VPS

  • Package as a Docker service alongside the existing Docker/Traefik setup — no need to expose it via Traefik unless a status dashboard is added later.
  • Restart policy: unless-stopped.
  • All secrets via environment variables injected at deploy time, not baked into the image.
  • Optional: a lightweight health-check/status endpoint for monitoring.

13 Suggested Build Order

  1. Data

    Binance read-only connectivity via ccxt, OHLCV storage, historical backfill. No exchange account credentials needed yet.

  2. Strategy + Backtest

    Pluggable strategy interface, at least strategies (a) and (b), backtesting harness with Quidax's real fee (0.1%) and a slippage assumption, across multiple regimes.

  3. Alerting

    Telegram integration, paper-mode signal alerts only (no execution).

  4. Cross-asset validation

    Before committing to a shadow run, re-run the exact fixed rule set from Phase 2 (no re-tuning) on ETH/USDT and 1–2 other liquid majors, same train/test windows. BTC has only one historical path, so repeated backtests against it aren't independent evidence — this is the fastest way to genuinely independent test data without waiting years for fresh BTC candles.

  5. Shadow run

    Live on the VPS in paper/alert-only mode for a few weeks, compared against backtest expectations before trusting it. Acceptance bar: "holds up near breakeven while meaningfully cutting drawdown and time-in-market versus holding," not "beats buy-and-hold."

    Concurrent shadow runs · 2026-09-07 — rather than testing one candidate at a time, the infrastructure runs multiple strategies concurrently against the same candle data, each with fully independent paper-trading state (keyed by strategy_label, no shared capital). docker-compose.yml runs the control (donchian_adx_control) alongside four candidates — multi_timeframe, donchian_natr_regime, vol_expansion, donchian_funding_filtered — as separate services sharing one SQLite file (WAL mode) and one Telegram chat.

  6. Execution (optional)

    Build the Quidax REST client, open a Quidax account + API key (trading scope only), manual-confirm mode first, full auto only after Phase 4 has proven out and the circuit-breaker/risk controls are tested.

14 Disclaimer

This spec is a technical build plan, not financial advice. No strategy here is guaranteed to be profitable — crypto markets are volatile and regimes change. Backtest thoroughly, paper-trade before risking capital, and only trade with money you can afford to lose. As of the most recent pilot testing (Section 8), none of the configurations tried so far have produced a result that clearly survives out-of-sample validation — expected at this stage, not a reason to abandon the approach, but it means Phase 5 (real execution) stays gated behind Phase 3.5 and a genuine Phase 4 shadow run, not opened on the strength of an in-sample backtest alone.
